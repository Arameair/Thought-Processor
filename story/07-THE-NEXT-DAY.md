### Nothing needs to be reborn

Maya opens Identity tomorrow.

It does not say **Create a new companion**. It finds the same durable installation, the same selected identity Compass, and her already-owned GitHub repository. It confirms the current account/repository where possible. It doesn't create another copy just because the application has restarted.

> **Welcome back**
>
> My GitHub repository: **Maya / my-companion**  
> Installation: **Restored from this local profile**  
> Working identity: **Compass**  
> Available features: **Checked / last verified**  
> Thought Processing: **Installed; requires the current local grant to operate**
>
> **[Open Thought Processor] [Inspect my repository] [Manage features]**

GitHub connection has special meaning: the initial product experience required verified account and repository ownership. A temporary outage today must be shown honestly as **verification unavailable**, not permission silently changed to yes. The exact policy for continuing already-running independent work during such outages remains an open owner decision. Repair must stay possible without throwing away existing data.

Maya opens Processor. It asks the launcher to **ensure the Engine is available**. If the same correct instance already runs, it attaches. If a previously session-owned Engine was explicitly stopped last night, the user-approved session can start it again. It uses the same durable Engine identity but a **new runtime instance ID**.

Her previous Traces remain Engine-owned. The companion's future long-term **Memory** will be another optional service with its own access and retention rules, not a magically existing archive inside Identity.

### An update arrives without taking her work away

One day, the publisher ships an updated approved starter or feature version.

Maya sees:

> **An upstream update is available**
>
> Your current starting version: **vA**  
> Available proposed version: **vB**  
> Source: **Original Arameair project**  
> Your local changes: **Will be compared, not silently overwritten**
>
> **[Review change] [Propose update in my repository] [Later]**

A controlled update could create a branch and pull request in Maya's repository for review. It must not silently force-push her edited source, rewrite credit, delete runtime logs, or treat publisher access to future features as implied local authorization. These exact update mechanics and software licensing are **still to be decided**.

She can keep using the features and data allowed by their actual terms, not by invented developer rules. The publisher can enforce access to new protected downloads and hosted services; already-delivered local code is not reliably revocable just by an editable toggle.

### The larger possibility, shown gently

Maya considers adding another source feature tomorrow: a game add-on, screen understanding, or a Discord bridge. Each would appear as an independently registered service, get a separate authorized relationship, and send relevant observations directly to Engine when permitted. Processor would help her discover and inspect it. Nothing in this first prototype requires building all of those.

She also imagines the system proposing changes to itself. **Dynamic coding remains a future, separately gated experiment** with human review, reproducible tests, promotion and rollback. No AI silently alters her owned repository just because a Thought is formed.

### The ending

The whole idea feels consistent: **her starting code and repository are hers; she can see which features she has access to, what data each may use, what is currently running, and what actually happened.**

Identity is the foundation. Processor makes the machinery understandable. Engine keeps performing its own work even when the screen is closed.

That is the promise we should decide whether we want to build.

**Blueprint seed:** Returning-installation restore, repository/update lineage, independent durable data, auth/entitlement revalidation, feature expansion and owner-approved evolution.
