## What you can run (START_HERE → TEST_P1)

[START_HERE.md](START_HERE.md) (clean WSL/Linux, ≈5 min build + 4 min tests) · [TEST_P1.md](TEST_P1.md) (≈15 min hands-on) · [FEATURE_API_V1.md](FEATURE_API_V1.md) (the language-neutral contract) · Identity side: [identity docs/P1_FEATURE_FOUNDATION_20261026.md](https://github.com/Arameair/identity/blob/experiment/p1-feature-foundation-claude-20261026/docs/P1_FEATURE_FOUNDATION_20261026.md).

1. **Original Admin Identity** — after a GitHub-verified sign-in, the owner explicitly establishes it in **Identity's own page** with a local passphrase (PBKDF2-HMAC-SHA256, 600k). Created once (atomic). GitHub numeric id bound as a sign-in alias. Switching GitHub accounts changes nothing.
2. **Elevated actions need a fresh Admin approval** bound to the exact action's SHA-256 (install, grant, uninstall). Processor can only *ask*; it never sees the passphrase. Works offline.
3. **Install** a manifest-driven package from a folder the operator trusted → Identity mints **one durable installation identity with zero grants** and a per-installation credential. Crash-safe, idempotent (same install key → same ID).
4. **Run** it standalone: manual / on-demand / always-running, real local API, signed heartbeat, deterministic self-test, idle stop (never during work), controlled recovery, orphan cleanup.
5. **Grant one capability** for a named requester (this Processor) and subject (Tass). The **receiving feature** verifies a ticket only Identity can sign for it, then asks Identity **live** before doing anything. Revoke → next request denied. Identity down → AUTHORITY UNAVAILABLE.
6. **Identity-first UI**: Admin, companions and installed features in one Identities workspace; feature tabs Overview · Connections · Runtime · Metrics · Logs; dark mode default (Light/System selectable, persisted).

## Self-audit: real vs fixture, and bypass search

- **Real:** every program, port, signature, approval, grant, ticket, live decision, process start/stop/crash and file on disk in the tests. No code path returns ALLOW without: an active grant created from a consumed Admin approval, a ticket signed with the recipient's key, and a live signed ALLOW from Identity that consumes it.
- **Labelled fixtures:** GitHub (Identity's `scripts/fixture_github_engine.py`, shown as TEST FIXTURE everywhere); the feature itself (`TRUSTED_LOCAL_TEST_FIXTURE`, SYNTHETIC TEST DATA); the "Admin" in automated tests is the harness typing the passphrase into **the same Identity page route** a browser uses.
- **Test hooks in shipped code (grep-verified):** `authority.SetIterationsForTests` (only called from `_test.go`); `TP_TEST_CRASH_POINT=after-register` (Processor exits — used to prove crash-safe install); the feature's `TEST-ONLY-fault-injection.json` (crash/delay **after** a live ALLOW, only if that file exists in its data folder). None can create, widen or fake a permission.
- **Fixed during self-review:** files crossing a symlinked folder; approval links now must point at the paired Identity's `/approve`; protected-action answers are now signed with the launch key so an impostor on the port can't fake `COMPLETED`.
- **Demonstrated limit, on purpose:** the integration test reads an installation's credential file as the same OS user and forges an *expired* ticket (refused) and an *unknown* ticket (refused by the live check). Same-user code can read secrets — see HIGH-1.

## Limitations, by severity

**HIGH**
1. **No OS isolation.** Features (and any other program) running as your user can read profile files — installation credentials, the Admin verifier, logs — and call loopback ports directly. Grants bind cooperating processes, not hostile ones. Mitigated only by refusing anything but trusted local fixtures. Must be solved (AppContainer / separate user / VM) before any third-party feature runs.
2. **Admin authenticator is a passphrase.** Same-user malware could guess it offline from `admin.json` (PBKDF2 600k slows this) or key-log the browser. Windows Hello / passkeys BLOCKED.
3. **Bootstrap is trust-on-first-use**: whoever controls the computer at first enrollment, with any GitHub account Identity verified, becomes Admin.
4. **Recovery deferred**: a forgotten passphrase makes the (disposable) profile's Admin unrecoverable; no fallback owner is ever created.

**MEDIUM**
5. Processor briefly holds each installation's credential (it writes it for the feature), so a compromised Processor could impersonate a feature to Identity.
6. Loopback HTTP is HMAC-authenticated, not encrypted.
7. Protected-action answers are signed only for the launcher (Processor). Other requesters rely on decision IDs.
8. Revoking is routine (owner's risk-based rule): any paired program can revoke any grant (denial-of-service, not escalation).
9. If Identity restarts on a different port while a feature runs, that feature keeps the old address → AUTHORITY_UNAVAILABLE until it is restarted (fails closed).
10. Signed-POST nonce ledger: ≤4 096 POSTs / 3 min per registry (≈22/s), then 503; rename-based writes, not fsync.

**LOW**
11. Windows: cross-compiles; supervisor uses no process groups there; nothing run on Windows.
12. The P0 Thought Engine release *download* path still exists (execution BLOCKED); its UI moved into the identity view.
13. Approval links are single-use: if a link preview "opens" it, ask again.
14. Exit always stops feature processes; "keep running" applies to Identity only.
15. Minimums: grant expiry 5 s, idle window 5 s.
