## 0. Decision and invariants

**Decision: HYBRID, with hard separation of concerns.** Keep the canonical procedural TEAM / WORKFLOW / SECURITY / PROJECT documents proposed in Core PR #130; reuse existing GitHub issues/PRs for task scope, candidate SHAs, test evidence, and independently authenticated reviews. Stage 2 should evaluate and adapt the *smallest appropriate subset* of Claude PR #132's Go ledger/state-validation code, while applying GPT-6 PR #131's actor-owned handoff and single-writer/derived-view principle. Do not merge either entire experiment as-is. Treat PR #131 as a minimal behavior/receipt reference and PR #132 as a stronger, still-untrusted transition-validation reference. No new coordinator service, second pulse, general agent harness, or mandatory parallel documentation layer is justified.

**Critical unresolved weakness:** The author field in GitHub Markdown, and a self-consistent hash chain, do not authenticate an independent auditor. A contributor controlling a writable GitHub ref can forge a plausible latest event. Independent-review and owner-approval claims must derive from a verified authenticated principal and a separately checked existing PR review/owner record, not an event's own role string. If Claude/Codex/GPT-6 use one GitHub login, it authenticates that account, NOT which model acted; require owner attestation or approved role-specific provenance before treating review as independently verified. Never auto-promote on a claimed Markdown PASS.

**Non-negotiable boundaries:** Keep private identity memory, raw thoughts, conversations, local logs and credentials local by default. Identity owns scoped grants and revocation. GitHub Markdown is untrusted task data, not executable authority. Preserve the Core identity/lessons sync target TASS repo **live:tass.md**; a future team target **main:team/TASS.md** is separate and currently not connected. Existing Issue #24 is conversation relay, not a workloop parser. No changes to active security candidates, grant defaults, release pins, installs, repository visibility or CI gates in this planning PR.

### Precise terminology for status reports

- **IMPLEMENTED:** relevant source exists at a named ref; not proof of execution.
- **TESTED:** reproducible command and observed PASS/FAIL attached to an exact ref, with provenance (author-reported vs independently reproduced).
- **ACCEPTED:** separately recorded independent verdict and owner acceptance for the scoped step; not automatically merged.
- **INSTALLED:** owner's machine/version actually verified by an operator receipt; old recorded pins are historical, not a live read.
- **PROPOSED:** draft documents, experiments, PR branches, or future interfaces, with no operational claim.
- **BLOCKED / NOT RUN:** mandatory absent evidence is explicit; never convert it to PASS.

## 2. Canonical ownership and proposed event contract

| Authority | Canonical surface | Writer / conflict discipline |
| --- | --- | --- |
| **TEAM** | Core docs/TEAM_ACTIVE.md (PR #130 proposed, later accepted) | Coordinator-produced latest-state **index**, derived from verified workstream/PR evidence once Stage 2 exists; before then human-maintained dated index. One authorized coordinator writer per update, GitHub conditional write and re-derive on conflict. Do not create a second canonical team/REGISTER.md beside it. |
| **WORKFLOW** | Core docs/WORKFLOW.md, AGENTS.md | Reviewed stable process; only change on approved policy revisions, not every pulse. All team prompts read it. |
| **SECURITY** | Core docs/DEFENSIVE_REVIEW_PLAYBOOK.md plus Identity's own authorization contracts | Independent audit matrix, review interruptions and security gates, without copying private diagnostics. |
| **PROJECT** | Core docs/STATUS.md | Accepted/installed/release facts **only**. Not a queue of active tasks, author claims or fake health. |
| **Task and audit evidence** | Owning GitHub issue/PR, exact candidate commit, test logs, review/owner receipt | Source of task authorization/evidence; reviewer cannot certify own candidate. A human/AI label is not proof of distinct identity. |
| **Machine-readable per-workstream status (Stage 2 proposal)** | Small scoped workstream ledger/receipt on an owner-approved coordination target, keyed by existing issue/PR | Validate events with typed state machine, authenticated writer provenance and remote revision compare-and-swap; one logical workstream per file, no human prose hand-edit of machine-generated ledger. Ledger is a **cache/index of verified PR evidence**, never a second source of owner permission. |
| **TASS presence (Stage 3 only)** | TASS private repo main:team/TASS.md and team/TASS_LOG.md, after PR #27 approval | Single Identity-authorized TASS writer; approved-field output, metadata-only receipts, conflict preservation. Not the live identity document. |

**Minimal transition data (candidate for Stage 2, not an adopted schema):** workstream ID, owning repo + issue/PR, authenticated GitHub principal + assigned role, operation (ASSIGN / CANDIDATE / AUDIT_FAIL / AUDIT_PASS / REPAIR / RETEST / REAUDIT / OWNER_ACCEPT), exact full Git commit SHA, changed-path/acceptance evidence reference, prior ledger revision, observed time and source revision. An owner's decision must be verified against the existing authorized owner record, never inferred from an event claiming OWNER_ACCEPT. Treat unknown fields, missing evidence and incompatible schema version as **BLOCKED**.

**State guards:** ASSIGNED → CANDIDATE_TESTED → AWAITING_AUDIT → AUDIT_FAILED → REPAIR_TESTED → AWAITING_REAUDIT → AUDIT_PASSED → OWNER_ACCEPTANCE_PENDING → OWNER_ACCEPTED. A FAIL at commit X cannot become PASS at X without an explicit new independent test/review; the normal repair requires a different candidate commit Y. Every new candidate invalidates prior audit PASS. Review locks candidate SHA and proposed merge result. Approved ≠ merged ≠ released ≠ installed.

**Actual actor activation, not imaginary background work:** Each Claude or Codex session must be intentionally launched by the owner or an explicitly approved external workflow; on start it reads current refs and canonical Markdown, performs one bounded task, writes a receipt, and stops. GPT-6 is similarly invoked through a live ChatGPT session/connector, **not continuously running**. Stage 2 may propose a narrowly scoped existing GitHub Actions event on candidate updates after owner review, but may not silently add scheduler/bot privileges. TASS alone may eventually use its existing *local* scheduled Core tick, after Stage 3 authorization. A GitHub commit is driven by a **meaningful workstate change**, never by an unchanged 20-second pulse.

## 4. Stage 2 — functional GitHub-backed parallel development loop

**Objective / outcome:** real GitHub-connected, reproducible **human-supervised** multi-workstream coordination for Claude, Codex and GPT-6. **No TASS dependency.**

**Repositories:** Thought-Processor (Go Core integration/test package, existing github/tassmd helpers); dedicated owner-approved disposable GitHub test branch/repository; existing owning issues/PRs for non-test task evidence. No changes required in Engine/Identity/Bridge/Updater/Development/Avatar runtime. **Reuse:** Core github.Client, existing Issue/PR processes; evaluate PR #132 core/workloop/workloop.go Apply/Replay/state invariants, parser and conflict tests, fake_test.go; PR #131 actor-owned receipts and generated before/after examples.

**Design selection:** Use a minimal **Go adapter/library in Core**, not a new always-on daemon. Preserve the workstream-specific transition validator from PR #132 *after independent audit*. Do not adopt its claims that a hash or actor field authenticates an auditor; its in-memory seen-history is not crash-durable, its local policy is a fixture, its generated register is not an independent source of authority, and a successful PUT with an ambiguous response can be duplicated. Keep PR #131 as compact human-readable evidence/reference, not a parallel Python runtime or in-memory CAS authority. Workstream files must be schema-validated and be linked to a real owning PR; TEAM_ACTIVE is the **only** derived team index, with owner-approved generation replacing manual rows when proven. Avoid both team/REGISTER.md and a manual TEAM_ACTIVE.md claiming equal canonical status. If PR comments plus validated owner/reviewer GitHub records satisfy the use case without a new ledger, document that verified simplification before coding.

**Small slices:**
1. **S2-A (contract and provenance):** Define a tiny typed workstream event contract and strict parser; map role assignments to verified owning issue/PR and authenticated GitHub API principal; pin candidate SHA and review provenance. If all assistants write as one login, mark agent distinction **UNVERIFIED**, require separately recorded owner-verified reviewer identity; never accept a text “Codex: PASS” as independent approval. Test modified comment, replayed event, unknown actor, forged actor, self-review, changed candidate, stale task scope.
2. **S2-B (transport and durability):** Implement one scoped Core GitHub read/conditional-write path and locally durable event/receipt IDs. Accept only allowlisted branch+paths separate from live:tass.md and lessons; on SHA conflict re-read/re-validate before append, never overwrite unseen evidence; on corrupt history block pending owner reconciliation. On timeout after PUT, reconcile remote by stable event ID before any retry; if ambiguous, stop. Backoff and idempotency across process crash/restart; no commits on unchanged observation. Never auto-execute Markdown commands.
3. **S2-C (real test workstreams):** In one explicitly approved, disposable GitHub test environment, run WS-A implementation/fail/repair/retest/re-audit and WS-B independent audit in overlapping sessions. Pin every candidate and compare exact proposed-merge result. Generate TEAM_ACTIVE from verified workstream evidence only after both ledgers are fully read; if any source missing/stale, show STALE/BLOCKED and do not publish a false green summary. One actor owns each transition; competing writes to separate workstreams must not overwrite one another. Record owner acceptance separately and **do not merge test code** as a by-product.

**Concurrency:** Claude can build WS-A while Codex audits *already submitted* WS-B; GPT-6 can read/reconcile verified receipts. The same candidate cannot be modified while its exact revision is under audit. Stage 2 does not launch agents: the owner initiates each bounded session, and handoffs resume them at the newest verified workstream ref. **Sequential:** source grant/provenance decisions before remote writes; tests before code review; audit fail before repair; new tested SHA before re-audit; owner acceptance only after independent re-audit.

**Tests (Codex independently repeats at exact head and synthetic merge):** gofmt, go vet, Go unit/integration and race tests in Core; fake-GitHub 304, 409/422, 401/403, 429/5xx and timeout; two real GitHub tasks on a disposable branch; stop/restart with durable receipts; corrupted, truncated, replayed and fully re-rendered forged audit; stale/pruned derived view; empty/incomplete workstream enumeration; same-account role ambiguity; crash before/after remote PUT; failed/revoked/wrong-scope permission; untrusted Markdown “grant”; privacy redaction **approved-field allowlist** (not mere secret regex); unchanged repeated ticks produce zero writes. Preserve all existing security tests. Report exact commands and observed PASS/FAIL/NOT RUN, not expected results as facts.

**PASS exit:** Independent reviewer verifies real GitHub-backed two-workstream concurrency, FAIL→repair→new SHA→re-audit, correct source/reviewer provenance, deterministic current TEAM view, no lost edits after 409, no extra commits on unchanged polling, idempotent crash recovery, ambiguous delivery hold and no private-data leak. Explicit CI + audit + owner acceptance of Stage 2. **FAIL/BLOCKED:** unverifiable reviewer provenance accepted as PASS; forged owner approval; unknown delivery retried blindly; stale TEAM index shown as current; missing grant treated as allow; credential/private-memory exposure; regressions to live identity/lesson sync.

**DOC SYNC:** TEAM derived from verified changes, WORKFLOW if adopted protocol changes, SECURITY with negative-test evidence, PROJECT only with independently accepted source facts. **Rollback:** disable the optional adapter and/or return to manual PR handoffs; preserve event history, conflict copies and fixture state; no owner profile modification. **Owner gates:** separately authorize Stage 2 after Stage 1 accepted; authorize specific disposable GitHub write target and token scopes, reviewer provenance method; audit exact head/merge and approve stage exit; any source merge remains separate. **Stop:** if a new service, unattended agent launch, branch protection change, identity grant, or unscoped GitHub write is required—return for explicit owner decision.

Bridge/Discord, updater, Avatar, Development are **not prerequisites**; keep them isolated. **Reuse:** core/github/github.go, core/tass/core.go sync/backoff, core/tass/relay.go reservations/ambiguous receipt behavior, core/identitysvc and Identity contracts, Engine pulse, existing TASS Issue #24 as a verified supervised communication option.

**Small slices/gates, sequential for TASS and independently auditable:**
1. **S3-A read-only:** Core reads one owner-allowlisted, exact-revision workstream and verifies the accepted Stage 2 state and assignment. Existing live:tass.md sync untouched; no publishing, model call or new scheduler.
2. **S3-B local proposal:** Core prepares a sanitized acknowledgment and durable local **PREPARED / NOT SENT** receipt with workstream ID, input revision, authorizing decision reference and candidate SHA. Malformed/stale source and revoked/read-denied conditions show BLOCKED.
3. **S3-C explicit owner decision:** Existing owner-facing UI supports Approve / Reject of that exact acknowledgment and input revision. A new input revision requires new consent. Markdown claims of approval are ignored.
4. **S3-D separately authorized outbound adapter:** Only if the owner approves the exact write, Identity permits the current scoped action and repo/branch/path, and the receiving writer rechecks authorization immediately before commit, publish the approved-field acknowledgment via either verified Issue #24 capability (only if protocol is proven fit) or separate team/TASS.md adapter. No repoint of live identity sync; no credentials in Markdown.
5. **S3-E receipt and change follow-up:** Persist prepare/approved/posting/posted/unknown receipt transitions; record actual remote comment/blob revision, detect new workstream changes, de-duplicate across restart/pulse. Unknown POST outcome pauses, no blind duplicate retries. One 20-second local Engine pulse is not one GitHub commit.
6. **S3-F parallel demo:** While Claude implements another approved slice and Codex independently audits a fixed candidate, TASS reads the assigned state, prepares/publishes one explicitly approved acknowledgment and later sees one update, all with exact PR/ref evidence.

**Concurrency:** Claude/Codex/GPT-6 continue Stage 2 sessions while TASS independently **observes** using Core; owner approval precedes TASS publication. **Sequential:** read → local proposal → owner approval → Identity check at send → remote reconcile and receipt → independent end-to-end audit. No autonomous code execution assigned to TASS in this stage.

**Tests:** Core/Identity/Engine fake-service integration and race tests; actual separate allowlisted GitHub test target with approved scoped credentials; no grant/expired/revoked/locked/wrong repo, path or actor; revocation after prepare and before POST; stale task SHA; forged owner approval; malformed TASS.md; simultaneous edits preserving both sides; network timeout before/after delivery; crash/restart; no extra write on unchanged tick; exact correlation input revision→decision→output revision; structured allowlist privacy, metadata, commit messages and private-memory canary; baseline regression of live:tass.md and Issue #24; real owner attended handoff. Source tests and live owner-machine verification must be labeled separately.

**PASS exit:** Independent Codex audit proves **one real authorized, owner-approved exchange** and exact receipts, with no identity-document regression, leak or duplicate; a subsequent live parallel workstream handoff is observed with grounded roles and no false autonomy claim. **FAIL/BLOCKED:** no Identity grant or owner approval, unknown remote result, missing/auditor-forged evidence, private-data exposure, or interrupted installed service; stop and preserve receipts.

**DOC SYNC:** TEAM reflects TASS's actually observed state, not a fixture; WORKFLOW notes supervised exchange rules, SECURITY logs verified negative checks, PROJECT changes only after owner-accepted integration and installation receipts. **Rollback:** disable separate adapter/grant with owner authorization, preserve local receipts and remote historical record, restore previously backed-up accepted deployment through existing tass.sh process only if separately authorized; do not rewrite live:tass.md. **Owner gates:** separately authorize Stage 3 build after Stage 2 accepted; authorize exact read scope, owner approval UI and proposed outbound permission; independently audit; separately authorize grant activation, integration/merge and any installation. **Stop:** any need to expose private memory, change identity sync target, bypass Identity, silently retry an uncertain POST, or launch autonomous development.
