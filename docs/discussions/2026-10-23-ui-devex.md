# Discussion agenda — UI and developer experience (2026-10-23)

**Status:** OPEN DESIGN DISCUSSION, not approved interface requirements and not implemented code.  
**Companion:** [Discovery, heartbeat and observability](2026-10-23-routing-heartbeat.md).  
**Attribution:** Notes prepared with AI assistance from the owner's direction and explicitly labeled design proposals.

## Aim

A developer observing from **Project Controller** should be able to open Thought Processor and understand whether the feature is genuinely connected and what the Thought Engine is doing, without reading every terminal or confusing connection with successful processing.

Keep the **Thought Processor application** distinct from **Project Controller**, which launches/displays branches: Project Controller owns Play/Stop of the Processor branch; Thought Processor shows and controls its feature connections. Neither silently assumes ownership of the external Engine, sources or worker.

## UI design options to discuss, not settle

**A. Overview-first**  
Top of screen: identity/grant, Engine, source feeds, worker, connection condition.  
Below: live activity timeline and a selected request's explanation.  
Benefit: at-a-glance status. Risk: hides the details a developer needs.

**B. Trace-first / debugger-first**  
Main area: live sequence `source event → engine decision → API heartbeat → worker result → thought update`.  
Side panel: selected stage details, raw/sanitized logs, exact errors and duration.  
Benefit: easier root-cause analysis. Risk: noisier for everyday operation.

**C. Split view**  
Compact status rail + live trace + expandable selected event inspection.  
Benefit: one screen for both health and explanation. Risk: more moving parts; should remain calm and scannable.

**No option chosen yet.** Avoid implementing mock buttons or a large dashboard before deciding which operator task comes first.

## A hypothetical developer walkthrough to validate

1. Open Processor from Project Controller and see `branch / SHA / process / port` clearly.
2. See **Identity permission**, **Engine connection**, **active feed(s)** and **worker readiness** as separate states.
3. Select an actual heartbeat in recent activity. Ask: which worker? request ID? when sent? reply status? elapsed time? what thought did the Engine change?
4. Click one failing stage to find the actionable reason and which independent component owns the fix.
5. Copy **one diagnostic context** with safe log references, exact versions and request/correlation IDs for another developer/AI to troubleshoot without guessing.
6. Stop the Thought Processor pane and verify independently running source/Engine/worker lifecycles are unaffected.

The numbers and controls shown in any future mockup must be labeled illustrative until connected to real data.

## Candidate minimum evidence fields

- Identity reference, entitlement verdict and verification age.
- Source and feed IDs, received/accepted events, last error.
- Engine endpoint, instance, branch/SHA, queue/process state.
- Selected worker endpoint/name/build/capabilities/readiness.
- Latest heartbeat request ID, status, submitted/completed times, measured duration.
- Thought result reference and persistence acknowledgment; if unknown say *unverified*.
- Error type, owning component, sanitized diagnostic logs, Copy Context.
- Clear state separation: **Not configured / Discovered / Connected / Authorized / Worker ready / Processing / Persisted / Degraded / Error** (these may represent different dimensions, not one mutually exclusive status).

## First UI questions for owner

1. **What should dominate the first screen?** A simple map of connected pieces, or the live stream of what the Engine is thinking/doing?
2. **What does “watching” mean?** Watching individual heartbeats in real time, inspecting completed thought chains, or both?
3. **Where should the full explanation be?** Inline expanding trace, side pane, or pop-out inspector?
4. **How should source/worker switching appear?** Read-only service selection first versus immediate controls; runtime change authorization remains OPEN.
5. **How much detail belongs in default view?** Show succinct diagnostics first, with full authorized input/output only on demand.
6. **What is the fastest debug loop?** Select failed heartbeat → copy context/logs → test/reconnect one affected component → verify a fresh heartbeat, while preserving earlier evidence.

## Proposed acceptance test for any UI prototype

Use one **real** Engine/worker/feed path. Cause a known failure. Without opening several terminals, the operator should identify **which stage failed**, **which process owns the failure**, the **request ID and error**, and whether a thought was persisted. Repeat after restart. Log measured time to diagnose, avoid reporting fixtures as live behavior.
